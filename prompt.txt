## Backend Performance Audit — investigate all areas

### A. Request pipeline & auth overhead

Every authenticated request passes through:

1. `AuthGuard` — `supabase.auth.getUser(token)` + Prisma user load with nested `userRoles → role → rolePermissions → permission`
2. `PermissionsGuard` (where applied)
3. `BranchGuard` (where applied)
4. MFA check: `requiresMfaPolicy(roles)` + JWT `aal` claim (skipped when `SKIP_ADMIN_MFA=1`)

**Investigate:**
- Is Supabase `getUser()` called on **every** request? Can JWT be verified locally (JWKS cache) instead?
- Is the full user+permissions graph loaded from DB on **every** request? Caching opportunities?
- Duplicate `/auth/me` work: frontend + server prefetch + guard
- Cost of deep Prisma `include` on auth path
- MFA guard latency for admin roles in non-demo environments

**Key files:** `apps/api/src/common/guards/auth.guard.ts`, `apps/api/src/modules/auth/auth.service.ts`

### B. Database & Prisma

**Investigate:**
- Missing indexes on `branchId`, `deletedAt`, `date`, foreign keys used in WHERE clauses
- N+1 queries in services (attendance sheets, student detail, parents with children, assessments/marks)
- Unbounded `findMany` without pagination (audit, communications logs, defaulters)
- Full table scans in analytics (e.g. `attendanceRecord.findMany` over date ranges loaded into memory)
- Sequential queries that could be `Promise.all` or single aggregated query
- Over-fetching: returning full relation trees when DTO needs fewer fields
- `count` + `aggregate` patterns in `reports.service.ts` — can they be combined or cached?
- Connection pooling: `DATABASE_URL` uses PgBouncer (port 6543) — Prisma config for pooler mode
- Transaction boundaries for bulk writes (attendance mark, marks bulk)

**Key files:** `packages/database/prisma/schema.prisma`, all `*.service.ts` under `apps/api/src/modules/`

### C. Hot endpoint deep-dives

Prioritize audit of these services/controllers:

| Module | Endpoints | Likely issues |
|--------|-----------|---------------|
| `reports` | `/reports/overview`, `/reports/fee-defaulters` | Multiple counts/aggregates per request |
| `analytics` | `/analytics/dashboard`, `/analytics/*` | In-memory aggregation over large record sets |
| `attendance` | `/attendance/sheet`, bulk mark | Large student lists per batch |
| `students` | list, detail, nested data | N+1 on detail page (6 parallel client queries) |
| `auth` | `/auth/me` | Called very frequently |
| `settings` | `/settings/institution`, lookups | Reference data; cacheable |
| `parents` | list with nested students | Join depth |
| `fees` | invoices, defaulters | Pagination, aggregates |
| `assessments` | marks sheet, bulk save | Batch size, validation overhead |

For each hot endpoint document:
- Prisma queries executed (count and shape)
- Rows touched (estimate with demo seed: ~49 students, ~500+ attendance records)
- Response payload size
- p50/p95 latency if measurable

### D. API design & payload

**Investigate:**
- Endpoints returning more data than the frontend uses
- Missing field selection / DTO projection
- List endpoints without pagination enforcement (max `limit=100` per docs)
- Duplicate endpoints fetching overlapping data (`/reports/overview` vs `/analytics/dashboard`)
- Opportunities for composite/dashboard endpoints to reduce round-trips (without breaking REST conventions)
- Compression (gzip/brotli) enabled in NestJS?
- Response serialization cost for large arrays

**Reference:** `docs/09-api-design.md`

### E. Caching & memoization (server-side)

**Investigate:**
- No HTTP cache headers on reference data (institution settings, lookups, branches, roles)
- No in-memory or Redis cache for expensive aggregates
- Whether analytics/report snapshots could be precomputed (materialized views, cron, or TTL cache)
- `ETag` / `If-None-Match` for settings endpoint
- Request-level memoization within a single request (dedupe identical Prisma calls)

### F. External dependencies

**Investigate latency from:**
- Supabase Auth API (`getUser` per request)
- Supabase Storage (document uploads)
- Email (Resend/SMTP), SMS (Twilio), OpenAI (AI modules) — not hot path but note async patterns
- OpenAI calls blocking request thread in `ai-attendance`, `ai-insights`

### G. NestJS runtime

**Investigate:**
- Global middleware overhead
- Validation pipe (Zod) cost on large payloads
- Module provider scope (singleton vs request)
- Logging verbosity in development affecting throughput
- `NODE_ENV`, clustering, and production deployment config (`docs/15-deployment.md` if present)

### H. Security vs performance trade-offs

Do not recommend optimizations that break:
- Branch-level data isolation (`branchId` filtering)
- Permission checks (`permissions.guard.ts`)
- MFA for `super_admin` / `branch_admin` in production
- Soft-delete filters (`deletedAt: null`)
- Audit logging requirements

Note where security checks add latency and suggest **safe** optimizations (e.g. cache permissions per user ID with short TTL).
